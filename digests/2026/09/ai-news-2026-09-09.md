### 1. 流体方程式の有限時間爆発を主張する2陣営が同時期に Lean 証明書を公開した — AI の数学的主張の検証が「論文の公開待ち」から「機械検証の再実行」へ移った

**要点**: OpenAI が Navier–Stokes ミレニアム問題の alternatives (C)(D) を、Alpöge–Buckmaster が smooth forcing つき 3D Euler の爆発を、それぞれ Lean 形式化つきで公開した。AI が出した数学的主張の確からしさを測る手段が、査読と論文公開を待つことから、**公開された形式化を自分で再検証すること**へ変わっている。

**詳細**: 双方の一次ホストは読めなかったが（`openai.com` はオリジン403、`terrytao.wordpress.com` と `www.nature.com` はゲートウェイ拒否）、**両陣営とも GitHub に Lean 形式化を公開している**ため、そこから確定した。

- **OpenAI 側**（`github.com/openai/NavierStokesAndEuler`・Apache-2.0）: 任意の正の粘性について、ℝ³ と周期トーラス ℝ³/ℤ³ の両方で「滑らかな初期値と外力が存在して、大域的な滑らかな解が存在しない」ことを形式化した。README はこれを Clay 数学研究所の公式問題記述の **alternatives (C)「Breakdown of Navier–Stokes solutions on ℝ³」と (D)** にあたると明記している。Lean は **4.34.0-rc2**
  - あわせて **外力なしの Euler** についても、滑らかでコンパクト台の非圧縮初期速度から有限時間で特異点が生じ、C¹ ノルムが非有界・渦度の L∞ ノルムの時間積分が発散することを形式化している
  - 独立検証は `ComparatorChallenges/` に手順があり、**Google DeepMind の Formal Conjectures による Navier–Stokes 問題文の Lean 定式化を参照ステートメントとして使い**、独立カーネル `nanoda_bin` で照合する形になっている
- **Alpöge–Buckmaster 側**（`github.com/tristanbuckmaster/fluid_lean`）: 非圧縮多孔質媒体（IPM）・2次元 Boussinesq・**3次元非圧縮 Euler の3本**について、**smooth forcing つき**の有限時間爆発を形式化した。Lean は **4.32.2**、Mathlib はコミット固定。`Challenge.lean` 以外に `sorry` は無く、依存公理は Lean 標準の3つ（`propext` / `Classical.choice` / `Quot.sound`）だけである
  - README は「このディレクトリの Lean コードはすべて **Claude が Levent Alpöge の指示のもとで書き、Alpöge は Lean を手書きしていない**」と記している
  - Terence Tao は、この構成が Córdoba–Martínez-Zoroa の手法を「空間方向にしか滑らかでない外力」から**完全に滑らかな外力**まで押し上げたものだと評価している（`terrytao.wordpress.com` 9/7 の投稿。本文は未読でスニペット経由）

⚠️ **経緯に係争がある。** OpenAI は 9/1 に噂を聞いて着手し 9/6 に自前の証明と Lean 検証を終えて両氏に連絡したところ、相手の対象が Navier–Stokes ではなく forced Euler だと判明したとしている。Buckmaster 側は、OpenAI が自分たちの進捗を知ってから同じ手法で着手したと述べている。OpenAI の Sebastien Bubeck はこれを否定している。**どちらの経緯が正しいかは本ダイジェストでは判定しない。**

⚠️ **二次が繰り返し書いた「OpenAI は証明を公開していない」は不正確である。** 公開されていないのは人間可読の論文2本（`formalization.yaml` が典拠として挙げる "Finite time blowup for Navier–Stokes" / "Finite time blowup for the Euler equation"）であって、**Lean 形式化と独立検証手順は公開されている**。⚠️ **一次未読**: 約10,000エージェント / 約88時間 / 270万メッセージ / 約1,300億出力トークン / GPT-6 Astra より高性能な未公開モデル、という規模の数値と、$100万の賞金を請求しない方針は**いずれも二次のみ**である。Clay 賞は公刊と2年以上の学界の受容を要件としており、いずれにせよ即時の授与はない。

### 2. Anthropic が Claude Platform のコスト最適化手順を公開し、Claude Code に測定用スラッシュコマンド3種を用意した — コスト削減が「プロンプトを短くする」から「アンチパターンを外して effort を測る」へ

**要点**: Anthropic が 9/8 にコスト最適化のガイドを公開し、**プロンプトのアンチパターン除去だけでコスト14.6%減・精度5.3%向上**という自社ベンチマーク結果を示した。削れる余地の在処が、トークン量そのものではなく**旧世代モデル向けに書かれた指示の残骸と effort の過剰指定**にあると位置づけられている。

**詳細**: 記事は `claude.com/blog/reducing-cost-and-improving-performance-with-claude-platform`。示された削減手段は3系統ある。

- **プロンプトキャッシュ**: prefill を再利用して入力単価の一部で済ませる。安定した接頭辞を先頭に置く、使用頻度の低いツール定義を後ろに回す、Console でヒット率を監視する
- **アンチパターンの除去**: フロンティアモデルの足を引っ張る旧世代向けの指示を外す。対象として「verify twice」のような検証儀式、不要な網羅性ブースター、手順の強制、scratchpad の足場、古い few-shot 例が挙げられている
- **effort の較正**: `effort` パラメータを段階的に振ってタスクごとの最適点を測る

Claude Code 側には測定用のスラッシュコマンド3種が用意されている。`/claude-api prompt-audit` がアンチパターンを検出し、`/claude-api cost-optimize` がトークン支出をプロファイルして削減レバーを試し、`/claude-api hillclimb` がモデル・effort・プロンプトの組み合わせを反復探索する。

数値は次のとおり。カスタマーサポートのベンチマークで **prompt-audit 単独でコスト14.6%減・精度5.3%向上**、**Fable 5.1 の low effort が Fable 5 の high effort に匹敵してコストは1/3**、公開ベンチマーク4本での最適化後のコスト削減幅は **52〜73%**。

⚠️ 数値はいずれも Anthropic 自身のベンチマークであり、第三者による再現報告は無い。
