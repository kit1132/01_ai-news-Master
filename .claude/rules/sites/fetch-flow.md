# ソース取得フロー

## 取得手順

各ソースの取得は以下の順序で試行する。

1. **プライマリURLをWebFetchで取得**
2. 403 / 429 / タイムアウトの場合 → **代替URLがあればWebFetchで試行**
3. それでも失敗した場合 → **WebSearchで `site:ドメイン 検索キーワード 当年` を実行**
4. `site:` 検索で結果0件の場合 → **`site:` を外して `検索キーワード 当年` で再検索**
5. すべて失敗した場合 → ダイジェストに「取得不可（手動確認推奨）」と記載

## RSS を取得したときの検証（ソフト200の罠）

RSS/Atom は **HTTP 200 が返っただけでは成功と判断しない**。次の2点を必ず確認する。

1. **Content-Type が `application/rss+xml` / `application/atom+xml` / `application/xml` / `text/xml` であること**
   - `text/html` が返っていたらフィードではない。実例: `https://cursor.com/rss.xml` は 200 を返すが `text/html` の約1.13MB の SPA（2026-07-26 実測）。パースすると失敗するか、空の結果を「更新なし」と誤認する
2. **最新エントリの日付が直近1ヶ月以内であること**
   - 200 でも中身が数年前で止まっているフィードがある。古いまま返るフィードは「更新なし」と区別できないので、鮮度を見て判断する

**リダイレクト先も確認する。** 実例: `https://forum.cursor.com/c/announcements/8.rss` は 301 で `/c/support/help/8.rss` に転送され、Help カテゴリの中身が 200 で返る（2026-07-26 実測）。バイト数だけを見ると成功に見えるため、意図したカテゴリの内容かをタイトルで確認する。

## 一次不通時の判定補助（B-020採用、2026-08-02）

一次（ベンダー公式 / `huggingface.co`）に到達できない状態で**オープンウェイトモデルの重み公開の有無**を書く場合、次の手順を踏む。

1. **二次情報が「重み公開済み」と「API 限定」で割れているときは、どちらか一方を採って断定しない**
2. 第三者の量子化リポジトリ（`*-GGUF` / `*-AWQ` / `*-MLX`）が**当該チェックポイント名を含む形**で存在するかを WebSearch で確認する。存在すれば「重み公開側の傍証あり」と併記する
3. それでも確定しない場合は、ダイジェスト本文に**「一次未到達のため未確定」と明記する**

実例（2026-08-02・DeepSeek-V4-Flash-0731）: 「HF の MIT ライセンス重みは4月 Preview のままで 0731 は API 限定」と書く記事と「DeepSeek は 0731 を HF に公開した」と書く記事が正面から矛盾した。一方で検索結果には `deepseek-ai/DeepSeek-V4-Flash-0731` の HF URL と、第三者の `unsloth/DeepSeek-V4-Flash-0731-GGUF` / `bullerwins/DeepSeek-V4-Flash-0731-GGUF` が同時に現れていた。**第三者が当該チェックポイント名の GGUF を公開できている事実は、重みが入手可能であることの傍証として強い。** 一次確認は `huggingface.co`（`/api/models/deepseek-ai/DeepSeek-V4-Flash-0731`）・`www.deepseek.com`・`api-docs.deepseek.com` がいずれも curl exit 56（ゲートウェイ拒否）で不可能だった。

## ⚠️ 上記の暫定手順は 2026-08-03 に終了した

**`huggingface.co` の疎通が回復したため、上節の「一次不通時の判定補助」は原則として使わない。**
環境のネットワークポリシーを `Custom` に変更し許可ドメインに `huggingface.co` を追加した結果、
`curl` 200 を確認した（B-013 / B-015 が要請していた許可リスト追加が実施された）。
本節冒頭の「疎通が回復したら一次確認に戻すこと」の条件を満たしたため、以後は次のとおり扱う。

- **重み公開の有無は `huggingface.co` で直接確認する。** モデルカードのほか
  `https://huggingface.co/api/models/<org>/<model>` が JSON を返すので、`siblings` のファイル一覧と
  `lastModified` で公開状態を機械的に判定できる
- **第三者の量子化リポジトリ（`*-GGUF` / `*-AWQ` / `*-MLX`）を傍証にする運用は畳む。**
  傍証は一次に到達できないときの代替であり、一次が読める状態で使うと精度を落とす

**ただし上節を削除はしない。** ベンダー公式サイト側が到達不可のまま HF も読めない状況
（例: `www.deepseek.com` / `api-docs.deepseek.com` は 2026-08-03 時点でゲートウェイ拒否が継続）では
同じ判断が再び必要になる。その場合に限り上節の①〜③を適用し、適用したことをダイジェスト本文に明記する。

## 403 を記録する前の判定順序（B-021採用、2026-08-06）

**403 を取得障害として台帳に記録する前に、必ず次の順序で判定する。**

1. **まず WebFetch を試す。成功したなら障害として記録しない。** 本文が取れているソースを障害として登録してはならない
2. WebFetch が失敗した場合に限り、`curl -sS -o /dev/null -w "%{http_code}" --max-time 25 <URL>` を実行する。
   `curl` の役割は**ゲートウェイ拒否とオリジン403の切り分けだけ**であり、取得可否の判定ではない
   - **ゲートウェイ拒否**: exit 56 / `CONNECT tunnel failed, response 403`。実行環境のネットワーク許可リスト外。
     サイト側が復旧しても解消しないので、週次復旧チェックではなく許可ドメイン追加で対処する
   - **オリジン403**: HTTP レスポンスとして 403 が返る。サイト側のブロック。WebSearch 運用へ切り替える
3. 2 の分類とともに `IMPROVEMENT-BACKLOG.md`「既知の取得障害」へ記録する

⚠️ **`curl` の 403 は WebFetch の可否を代表しない。** 2026-08-03 の週次復旧チェックで `github.com` 配下3 URL
（`github/copilot-cli/releases`・`openai/codex/releases`・`openai`）はいずれも `curl` が HTTP 403 を返したが、
**同一セッションの WebFetch は本文取得に成功**し Copilot CLI と Codex CLI の最新リリースを一次で確定できている。
`github.com` は本ファイルおよび `daily-sources.md` で「WebFetch 安定」と明記している一次ソースであり、
`curl` の結果だけで記録すると**毎日取得できているソースを障害として登録してしまう**。

## フォールバック発生時の記録ルール

フォールバック（手順2以降）を使用した場合、リポジトリルートの **`IMPROVEMENT-BACKLOG.md`「既知の取得障害」セクションを更新する**。ダイジェストの改善メモに書くのは「変化があったもの」だけ。

- **新規の障害**（台帳にない URL）: 台帳に以下の形式で1行追加し、ダイジェストの改善メモにも「障害の変化」として1行記載する

  ```
  - <ソース名 / URL>: <403/429/timeout>（初出 YYYY-MM-DD / 最終確認 YYYY-MM-DD）→ 回避策: <成功した方法 / なし（取得不可・手動確認推奨）>
  ```

- **既知の障害**（台帳にある URL）: 台帳の「最終確認」日付を更新するのみ。**ダイジェストには書かない**
- **復旧**（台帳で障害扱いの URL が正常取得できた）: 台帳の該当行の行末に `→ 復旧（YYYY-MM-DD）` を追記し、ダイジェストの改善メモに「障害の変化」として記載する。行は削除しない
- **回避策が安定している長期障害**: `daily-sources.md` の取得方法欄を回避策ベースに書き換える提案を、台帳の「提案中」に起票する（既に同趣旨の提案があれば回数を +1 するだけ）

## 復旧チェック（週1回・月曜）

`IMPROVEMENT-BACKLOG.md`「既知の取得障害」に記載されている403継続ソースに対し、**毎週月曜の生成セッションで**以下を実行する（B-001採用、2026-06-10）：

1. 各障害ソースのプライマリURL（RSS含む）に WebFetch / RSS 取得を試行する（`curl` から始めない。上節「403 を記録する前の判定順序」と同じ理由）
2. **復旧していた場合**: 台帳の該当行に `→ 復旧（YYYY-MM-DD）` を追記し、`daily-sources.md` の取得方法欄を元に戻す。ダイジェストの改善メモに「障害の変化」として記載する
   - ⚠️ **取得方法欄を戻すのは、そのソースで実際に本文取得が成功したときだけ**にする。`curl` 200 は許可リストを通過した証拠にすぎず、本文が取れることまでは示さない（実例: 2026-08-04 の8ホスト復旧では、5ソースで本文取得を確認したうえで 08-06 に取得方法欄を戻した＝B-023採用）
3. **継続していた場合**: 台帳の最終確認日を更新するのみ（ダイジェストには書かない）

月曜以外の日はこのチェックを行わない（通常のフォールバックフローのみ）。

## WebSearch利用時の注意事項

- `site:` オペレータは非対応の場合がある。結果0件なら必ず `site:` を外して再検索する
- WebSearchに日付フィルタ機能はない。クエリに年（例: `2026`）を含めて新しい結果を優先する
- インデックス反映に数時間〜数日のラグがある。速報性が必要な情報には限界がある
- WebSearch結果はURLとスニペットのみの場合がある。必要に応じて結果内のURLをWebFetchで追加取得する
