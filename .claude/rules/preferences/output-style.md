### 今日のハイライト（2026-07-26 追加）

ダイジェストの冒頭に `## 今日のハイライト` を置き、**最重要2〜3件**を
`### N. タイトル — 一言の含意` の見出しに続けて
**要点** / **詳細** の2段落で書く。末尾に出典URLを箇条書きで付ける。

- **要点**: 何が起きて、**つまり前提が何から何へ変わったか**まで書く。**120字以内**。
  事実の要約で終わらせない。ここだけ読んで「読むか飛ばすか」を判断できるようにする
- **詳細**: 数値・スペック・日付・経緯。事実の裏付けを兼ねる

**「意味」段落は 2026-07-31 に廃止した。**
so what を400字超の「詳細」の後ろに置くと、結論が壁の向こう側になって読まれない。
2026-07-31 実測では要点93字（事実の要約のみ）→詳細435字→意味237字（so what）の順で、
結論に辿り着くまでに528字を読ませていた。so what は要点に統合する。
**要点の80字→120字はこの統合ぶんの増枠であり、詳細を水増ししてよいという意味ではない。**

**書かないこと**:
- 一般論の助言（「〜を要件化すべき」「〜から着手するのが妥当」等）。読まれていないため廃止した。
  要点に統合した so what は「前提が何から何へ変わったか」であって「〜すべき」ではない。ここを混同しない
- 材料がない段落を無理に埋めること。**該当する内容がなければその段落は省略する**

**ハイライトは2〜3件まで。全項目をこの形式にしない。**

カテゴリ項目にも「結論を先に、裏づけを後に」の構造は**既に入っている**
（第1文ルール 2026-07-28、列挙の外形化 2026-07-31）。違いは `**要点**` / `**詳細**` のラベルを貼るかどうかだけである。
それでもラベルを貼らないのは次の2点による。

1. **序列が消える** — `.lbl` のラベル列と左の色罫は、ビューア上でハイライトを他と区別している唯一の装置である。
   全項目に付けると「今日の N 件」が同じ見た目のブロックに埋没し、どれを先に読むかが分からなくなる
2. **縦幅が増える** — 2026-07-31 の実測（375×812・全節開・05 daily の公開版）で、カテゴリ親項目20件に
   要点/詳細を貼ると **+1.8画面**（18.5 → 20.3画面・+10%）。モバイルはラベルが縦積みになるため1個あたり37px 効く

⚠️ 旧根拠「全項目を段落形式にすると 01 で3.0倍・02 で2.2倍に膨らむ」（2026-07-26 実測）は
**要点/詳細/意味 の3段落時代の測定**であり、「意味」を廃止した 2026-07-31 以降は当てはまらない。
2026-07-31 に上記の理由へ差し替えた。

ハイライト以外は下記の箇条書き形式のまま残すこと。

### ハイライトの選定基準（2026-07-31 追加）

**「最重要」の定義が無かったため、同じ日の同じ入力から違う件数・違う顔ぶれが選ばれていた。**
2026-07-31 の日次サマリーには2つの版が存在し、3件目が「Claude 共有リンクの検索エンジン露出」と
「Power Automate 3機能の GA」で割れていた。基準を以下に固定する。

次のいずれかに当たるものだけをハイライトにする。該当が上限件数を超える場合は **1 → 2 → 3 の順**で採る。

1. **不可逆な期限がある** — 退役日・廃止日・ポリシー発効日など、見逃すと取り返せないもの
2. **前提が壊れた** — 価格・仕様・可用性が変わり、既存の試算や提案を引き直す必要があるもの
3. **今日から手が動く** — kit が使っているツール（Claude Code / Copilot / Cursor / Power Platform / AWS）の
   挙動・権限・料金が変わり、当日から操作や設定が変わるもの

**ハイライトにしないもの**（カテゴリ別まとめに置く）:

- 「更新なし」「据え置き」「変化なし」の報告。変化がないものに so what は無い
- **既報の再掲**。一度ダイジェストに載せた話題を、続報なしで再びハイライトにしない。
  ⚠️ **「出来事が古いこと」と「既報であること」は別である。**発生が2週間前でも、
  **本日はじめて判明した事実**はハイライトの対象にしてよい（例: Release Wave の緑チェックだけが
  一次シグナルで、GA から2週間後に検知した機能）。除外するのは既に載せた話題の蒸し返しだけ
- 公式未確認の観測・推定だけで成り立つ話題

該当が1件も無い日は、**ハイライトを2件・1件に減らしてよい**。件数を埋めるために基準を緩めない。

### ハイライト以外（カテゴリ別まとめ）

- カテゴリ分類 + 要約
- 各項目2-3行で簡潔に
- 全体で5-15項目が目安
- ソースURLは必ず含める
- rebrand・組織再編・提携・GTM変更系の話題は「企業構造 / GTM 動向」セクションとして独立させる（該当ニュースがある日のみ。B-008採用、2026-06-10）

## 列挙の外形化（2026-07-31 追加）

**地の文に並列列挙が3つ以上現れたら、ネストした箇条書きに外形化する。**

これまでのルール（太字・第1文）はすべて *文レベル* の規定で、**構造レベルの規定が1つも無かった**。
そのため列挙が地の文に埋め込まれたままになり、読み手の目が休まる場所が無くなっていた。

### 判定シグナル（どれか1つでも当たれば外形化する）

- `①②③` のような丸数字を使っている（記号を使った時点で、書き手は列挙だと自覚している）
- 中黒 `・` で **6字以上の句を3つ以上**連ねている
- 読点 `、` で **6字以上の並列句を3つ以上**連ねている

⚠️ **「6字以上」は 2026-08-01 に追加した制限。** 初版は「中黒で3語以上」と書いていたが、
実データに当てると **9件中6件が誤検出**だった（`scripts/measure-density.py` で実測）。

```
（誤検出＝外形化しなくてよい）
  10万人の科学者・数学者・技術者へフロンティアモデルを提供する
  歩行・しゃがみ・物体操作を対象にした
  文書・地理情報・部隊運用情報を統合して分析する

（外形化の候補＝各要素が長く、独立した情報を持つ）
  アクティブ開発者数・セッション数・組織横断の頻出コマンドが日次更新で表示される
```

**短い名詞の並列は文の一部であって、行を分ける対象ではない。**
`①②③` は長さにかかわらず外形化する（記号の使用そのものが列挙の自覚を示すため）。

### 書き方

- 親行に「何が公開された/変わったか」を書き、内訳を子行に落とす
- 各子行は **識別子: 中身** の形にする。機能名・API 名・製品名を行頭に出すと目が拾える
  - ⚠️ **バッククォートで囲むのは英数字の識別子だけ**（`EmailActions`・`embedded_resource_snapshot_id` 等）。
    **日本語の見出し語は囲まない。** `code` は等幅フォントに切り替わり、日本語が混じると環境によって
    明朝系にフォールバックして本文（ゴシック）と書体が混在する（2026-07-31 実測・8箇所で発生）
  - 日本語の見出し語は**装飾なしで行頭に置く**。行頭にあること自体が目印になるので太字も不要
    （太字は「1項目3箇所まで」の枠を食う）
- **1項目1行に機械分割しない。** 序列の低いものはまとめて1行にする

### 目的は字数削減ではない

外形化しても字数はほとんど変わらない（下の例で約230字→約250字）。
**改行が「並列であることの合図」と「目の休憩場所」を同時に作ることが目的**である。
字数を理由に外形化を見送らないこと。

## 第1文の書き方（主体と述語）（2026-07-28 追加）

カテゴリ別項目の**第1文は、それ単独で意味が通る完全文にする**。

⚠️ **このルールが掛かるのは説明側だけである。**見出しに相当する部分
（`**ラベル**:` のラベル、`タイトル — 説明` のダッシュより前）は文ではなくラベルなので、
`Gemini 3.5 Pro は未 GA が継続` のように体言止めでよい。述語で終える必要はない。

- 第1文（説明側）は「〈主体〉が〈何を〉〈どうした〉」の形にし、**述語（動詞・助動詞）で終える**
  - 禁止: 「〜可能に。」「〜追加。」「〜対応。」「〜開始。」「〜提供。」のような体言止め
  - 可: 「〜できるようになる。」「〜を追加した。」「〜に対応し GA した。」
- 主体が2つある場合は**操作・受益主体を優先**する
  - 操作・受益主体 = 誰が設定するか / 誰が使えるようになるか（開発者・管理者・エンドユーザー・対象プラン）
  - 発表主体 = 誰が出したか（Anthropic / OpenAI / Google / Cursor 等）。
    **本リポジトリは複数ベンダーが混在するため、発表主体は原則として省略しない**（誰の発表かが情報になる）
- 太字ラベル（`**機能名**:`）は残す。ただしラベルは *モノの名前* であって主体ではないので、
  **ラベルがあっても主語を書いたことにはならない**。ラベルを隠しても第1文だけで通じること

**適用除外**: 将来日付のイベントを日付順に並べる節（「注目スケジュール」等）と、「（ハイライト参照）」だけの行。

```
（悪い）Codex に **ChatGPT Voice** とローカルプロジェクトの複数フォルダ対応（7/23）
（良い）OpenAI が Codex に ChatGPT Voice を追加し、ローカルプロジェクトで複数フォルダを登録できるようにした（7/23）

（悪い）LLM トークンの「リレー市場」調査（7/26）  ← 誰が調べたのか分からない
（良い）Vectoral が、集めた API キーをプールして LLM アクセスを転売する市場の実態を調査した（7/26）
```

2026-07-27 の実測（各ソース最新10ファイル・ハイライト・改善メモ・日付一覧を除く）では、
**主語よりも「述語で終わらないこと」が壊れていた**。

| ソース | 項目数 | 主語あり | 述語で終わる | 両方満たす | 項目平均字数 |
|---|---|---|---|---|---|
| **Master** | **46** | **54%** | **26%** | **22%** | **306字** |
| Copilot | 108 | 44% | 31% | 11% | 154字 |
| industry | 70 | 46% | 16% | 14% | 134字 |
| weekly | 580 | 33% | 6% | 2% | 113字 |
| daily | 116 | 51% | 26% | 17% | 197字 |

主語（〜が / 〜は）は33〜54%残っているのに、述語で終わるのは6〜31%しかない。
主体を書いても体言止めで終えると「結局どうなったのか」が宙に浮くため、**両方**を守ること。

⚠️ **文字数と引き換えにしない。** このルールは文を長くする方向に働く。
「トーン」節の「冗長な前置き不要」は引き続き有効で、**項目平均字数 367字（＝適用前306字の+20%）を超えたら書きすぎ**。
02 Copilot に先行適用した 07-28 分では、述語で終わる率 31%→91% に対し項目平均字数は 154字→155字（+0.6%）だった。

## 太字（`**...**`）の使い方

太字は「あとで検索・引用したくなる語」だけに使う。**文や節をまるごと太字にしない**。

- **1項目（`###` 単位）につき太字は3箇所まで**
- **1箇所は20字以内**の語句に限る。それを超える長さは太字にしない
  - ⚠️ **例外: 固有名詞そのもの**（製品名・ページ名。`M365 Copilot Release Notes`・`GitHub MCP と Playwright MCP` 等）は
    20字を超えてよい。禁止したいのは「文・節をまるごと太字にすること」であって、名前が長いことではない（2026-07-31 追加）
  - **述語で終わる文は太字にしない。** 項目の見出しを結論の文にする場合は太字ではなく ` — ` 区切り
    （`結論の文 — 説明`）を使う。ビューアはダッシュの手前を見出しとして立てるが、20字超の太字は逆に
    ウェイトを落とす処理（`decorateBold`）に掛かり、**結論が弱く表示されてしまう**
- 対象は固有名詞＋バージョン（`Claude Code v2.1.220`）、金額（`$100M`）、日付、`%` などの数値
- 強調したい主張は太字ではなく**文の順序**（結論を先に書く）で示す
- 目安: 本文の太字比率は **10%以下**

2026-07-26 の実測（各ソース最新10ファイル・改善メモ除外）では、太字が
「多すぎる」と「1回が長すぎる」の2つの形で崩れていた。

| ソース | 太字率 | 1項目あたり | 1箇所の平均長 | 20字超の割合 |
|---|---|---|---|---|
| Copilot | 21.5% | 4.7箇所 | 26.1字 | 59% |
| daily | 18.7% | 4.6箇所 | 18.9字 | 40% |
| Master | 13.3% | 4.4箇所 | 15.6字 | 34% |
| weekly | 8.2% | 2.6箇所 | 14.3字 | 27% |
| industry | 6.5% | 0.5箇所 | 41.6字 | 82% |

太字が本文の2割を占めると、どこが重要かが判別できなくなる（太字が意味を失う）。
industry のように「回数は少ないが1回が41字」も同じ結果を招くため、回数と長さの
両方を守ること。

## 技術記事の型（2026-08-06 追加）

⚠️ **本節は日次ダイジェストには適用しない。** `digests/YYYY/MM/ai-news-YYYY-MM-DD.md` は
上の「フォーマット」節（ハイライト＋カテゴリ別箇条書き）のままとする。
本節が掛かるのは、**複数の対象を同じ観点で並べて論じる単体記事**（横断調査・比較・棚卸しの報告）である。

### 構成

```
見出し（主張を含む） — サブタイトル（読者の前提が何に変わるかを一文で）
```

- **要点**: 5〜6行。対象・件数の内訳・共通する結論・前提の変化
- **本体**: 比較対象ごとに1節。**件数がゼロの対象も必ず1節を立てる**（不在が情報になる）。
  各節の見出しは `対象名 — 件数と状態` の形にする。節内は識別子（CVE番号など）を太字で立て、直後に説明を続ける
- **共通する経路**（該当があれば）: 個別対象に帰属しない論点をここに集約する
- **関連**（該当があれば）: 主題の外側だが読者に関わる情報。**本体に混ぜない**

### 生成手順

**本文を書く前に、比較の軸を1つ宣言し章立てだけを出す。**
軸は見出しで宣言した数と一致させる。**承認後に本文を書く。**
調査した順序ではなく、この型の順序で並べる。

### 事実の扱い

識別子・バージョン・日付は**出典に無い値を書かない**。
主題の枠組み（イベント名など）と矛盾する日付があれば、**修正せず指摘する**。

### 既存ルールとの関係

- **「太字は1項目3箇所まで」の上限は、本体節の識別子には掛けない。** 識別子（CVE番号・バージョン・製品名）は
  「あとで検索・引用したくなる語」の典型であり、太字節の趣旨に合致する。ただし**1箇所20字以内**は維持する
- 「第1文の書き方」（主体と述語）は**説明側にそのまま掛かる**。`対象名 — 件数と状態` の見出しはラベルなので体言止めでよい
- 「列挙の外形化」も掛かる。本体節の中で並列が3つ以上出たらネストした箇条書きに落とす
- 「ハイライトの選定基準」は掛からない。本型に**ハイライトは無く、序列は本体節の並び順で示す**

**⚠️ 絶対ルール: 改善メモを書く前に、必ずリポジトリルートの `IMPROVEMENT-BACKLOG.md` を読み、台帳を先に更新すること。** 台帳の運用ルールは同ファイル冒頭を参照。

### ダイジェストに書く内容（台帳との差分要約のみ・3〜6行が目安）

- **新規提案**: 本日新たに起票した提案の ID と一行要約（例: `B-011: Codex CLI changelog をソース追加（詳細は台帳）`）
- **継続提案**: 件数サマリ1行のみ（例: `継続提案 5件（最多: B-001 復旧チェック手順、12回目）`）。**個別内容の再掲は禁止**
- **障害の変化**: 新規発生・復旧など変化があった場合のみ1行ずつ。既知障害の「継続中」報告は書かない
- 変化がない日は `- 新規提案・障害の変化なし（継続分は IMPROVEMENT-BACKLOG.md 参照）` の1行のみとする

### 書いてはいけないもの（禁止）

- ニュース内容に関する気づき・考察 → ダイジェスト本文の該当項目に書く
- 正常に取得できたソースの列挙・状況報告 → どこにも書かない
- 既出提案・既知障害の繰り返し記載 → 台帳の「最終確認 / 回数」の更新のみで表現する

### 新規提案の品質基準

- 台帳への起票には「対象（ファイル・セクション）/ 変更内容 / 根拠」を必ず含める。「〜を検討」「〜推奨」だけで対象と変更内容が特定できない起票は禁止
- 起票前に対象の rules ファイルの現在の記載を確認し、**既に決定・記載済みの内容と矛盾・重複する提案をしない**（過去に「月1回の復旧チェック」決定済みにもかかわらず「週次テスト」を3日連続提案した前例があるため）
