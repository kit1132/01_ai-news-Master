### 今日のハイライト（2026-07-26 追加）

ダイジェストの冒頭に `## 今日のハイライト` を置き、**最重要2〜3件**を
`### N. タイトル — 一言の含意` の見出しに続けて
**要点** / **詳細** / **意味** の3段落で書く。末尾に出典URLを箇条書きで付ける。

- **要点**: 何が起きて、なぜ重要か。**1〜2文・80字以内**。ここだけ読んで「読むか飛ばすか」を判断できるようにする
- **詳細**: 数値・スペック・日付・経緯。事実の裏付けを兼ねる
- **意味**: kit の仕事（AI/クラウド開発、コンサル提案）にどう関わるか

**書かないこと**:
- 一般論の助言（「〜を要件化すべき」「〜から着手するのが妥当」等）。読まれていないため廃止した
- 材料がない段落を無理に埋めること。**該当する内容がなければその段落は省略する**（3段落を必ず埋めなくてよい）

**ハイライトは2〜3件まで。全項目をこの形式にしない。**
2026-07-26 の実測では、全項目を3段落化すると本文が 01 で3.0倍・02 で2.2倍に膨らむ。
ハイライト以外は下記の箇条書き形式のまま残すこと。

### ハイライト以外（カテゴリ別まとめ）

- カテゴリ分類 + 要約
- 各項目2-3行で簡潔に
- 全体で5-15項目が目安
- ソースURLは必ず含める
- rebrand・組織再編・提携・GTM変更系の話題は「企業構造 / GTM 動向」セクションとして独立させる（該当ニュースがある日のみ。B-008採用、2026-06-10）

## 第1文の書き方（主体と述語）（2026-07-28 追加）

カテゴリ別項目の**第1文は、それ単独で意味が通る完全文にする**。

- 第1文は「〈主体〉が〈何を〉〈どうした〉」の形にし、**述語（動詞・助動詞）で終える**
  - 禁止: 「〜可能に。」「〜追加。」「〜対応。」「〜開始。」「〜提供。」のような体言止め
  - 可: 「〜できるようになる。」「〜を追加した。」「〜に対応し GA した。」
- 主体が2つある場合は**操作・受益主体を優先**する
  - 操作・受益主体 = 誰が設定するか / 誰が使えるようになるか（開発者・管理者・エンドユーザー・対象プラン）
  - 発表主体 = 誰が出したか（Anthropic / OpenAI / Google / Cursor 等）。
    **本リポジトリは複数ベンダーが混在するため、発表主体は原則として省略しない**（誰の発表かが情報になる）
- 太字ラベル（`**機能名**:`）は残す。ただしラベルは *モノの名前* であって主体ではないので、
  **ラベルがあっても主語を書いたことにはならない**。ラベルを隠しても第1文だけで通じること

**適用除外**: 将来日付のイベントを日付順に並べる節（「注目スケジュール」等）と、「（ハイライト参照）」だけの行。

```
（悪い）Codex に **ChatGPT Voice** とローカルプロジェクトの複数フォルダ対応（7/23）
（良い）OpenAI が Codex に ChatGPT Voice を追加し、ローカルプロジェクトで複数フォルダを登録できるようにした（7/23）

（悪い）LLM トークンの「リレー市場」調査（7/26）  ← 誰が調べたのか分からない
（良い）Vectoral が、集めた API キーをプールして LLM アクセスを転売する市場の実態を調査した（7/26）
```

2026-07-27 の実測（各ソース最新10ファイル・ハイライト・改善メモ・日付一覧を除く）では、
**主語よりも「述語で終わらないこと」が壊れていた**。

| ソース | 項目数 | 主語あり | 述語で終わる | 両方満たす | 項目平均字数 |
|---|---|---|---|---|---|
| **Master** | **46** | **54%** | **26%** | **22%** | **306字** |
| Copilot | 108 | 44% | 31% | 11% | 154字 |
| industry | 70 | 46% | 16% | 14% | 134字 |
| weekly | 580 | 33% | 6% | 2% | 113字 |
| daily | 116 | 51% | 26% | 17% | 197字 |

主語（〜が / 〜は）は33〜54%残っているのに、述語で終わるのは6〜31%しかない。
主体を書いても体言止めで終えると「結局どうなったのか」が宙に浮くため、**両方**を守ること。

⚠️ **文字数と引き換えにしない。** このルールは文を長くする方向に働く。
「トーン」節の「冗長な前置き不要」は引き続き有効で、**項目平均字数 367字（＝適用前306字の+20%）を超えたら書きすぎ**。
02 Copilot に先行適用した 07-28 分では、述語で終わる率 31%→91% に対し項目平均字数は 154字→155字（+0.6%）だった。
**文字数を増やさずに達成できる**。測定は `scripts/measure-subject-rate.py`（01_ai-news 親ディレクトリ）で行う。

## 太字（`**...**`）の使い方

太字は「あとで検索・引用したくなる語」だけに使う。**文や節をまるごと太字にしない**。

- **1項目（`###` 単位）につき太字は3箇所まで**
- **1箇所は20字以内**の語句に限る。それを超える長さは太字にしない
- 対象は固有名詞＋バージョン（`Claude Code v2.1.220`）、金額（`$100M`）、日付、`%` などの数値
- 強調したい主張は太字ではなく**文の順序**（結論を先に書く）で示す
- 目安: 本文の太字比率は **10%以下**

2026-07-26 の実測（各ソース最新10ファイル・改善メモ除外）では、太字が
「多すぎる」と「1回が長すぎる」の2つの形で崩れていた。

| ソース | 太字率 | 1項目あたり | 1箇所の平均長 | 20字超の割合 |
|---|---|---|---|---|
| Copilot | 21.5% | 4.7箇所 | 26.1字 | 59% |
| daily | 18.7% | 4.6箇所 | 18.9字 | 40% |
| Master | 13.3% | 4.4箇所 | 15.6字 | 34% |
| weekly | 8.2% | 2.6箇所 | 14.3字 | 27% |
| industry | 6.5% | 0.5箇所 | 41.6字 | 82% |

太字が本文の2割を占めると、どこが重要かが判別できなくなる（太字が意味を失う）。
industry のように「回数は少ないが1回が41字」も同じ結果を招くため、回数と長さの
両方を守ること。

## トーン

- 冗長な前置き不要
- 事実ベース、感想は不要
- 重要度が高いものほど上に配置
- 情報が少ない日は無理に増やさない（「特筆事項なし」でOK）
- 長すぎる説明・お世辞・精神論は不要

## 改善メモ（バックログ方式）

ダイジェスト末尾に「## 改善メモ」セクションを設ける。

**⚠️ 絶対ルール: 改善メモを書く前に、必ずリポジトリルートの `IMPROVEMENT-BACKLOG.md` を読み、台帳を先に更新すること。** 台帳の運用ルールは同ファイル冒頭を参照。

### ダイジェストに書く内容（台帳との差分要約のみ・3〜6行が目安）

- **新規提案**: 本日新たに起票した提案の ID と一行要約（例: `B-011: Codex CLI changelog をソース追加（詳細は台帳）`）
- **継続提案**: 件数サマリ1行のみ（例: `継続提案 5件（最多: B-001 復旧チェック手順、12回目）`）。**個別内容の再掲は禁止**
- **障害の変化**: 新規発生・復旧など変化があった場合のみ1行ずつ。既知障害の「継続中」報告は書かない
- 変化がない日は `- 新規提案・障害の変化なし（継続分は IMPROVEMENT-BACKLOG.md 参照）` の1行のみとする

### 書いてはいけないもの（禁止）

- ニュース内容に関する気づき・考察 → ダイジェスト本文の該当項目に書く
- 正常に取得できたソースの列挙・状況報告 → どこにも書かない
- 既出提案・既知障害の繰り返し記載 → 台帳の「最終確認 / 回数」の更新のみで表現する

### 新規提案の品質基準

- 台帳への起票には「対象（ファイル・セクション）/ 変更内容 / 根拠」を必ず含める。「〜を検討」「〜推奨」だけで対象と変更内容が特定できない起票は禁止
- 起票前に対象の rules ファイルの現在の記載を確認し、**既に決定・記載済みの内容と矛盾・重複する提案をしない**（過去に「月1回の復旧チェック」決定済みにもかかわらず「週次テスト」を3日連続提案した前例があるため）
